## Почему EXE не превращается обратно в исходный Go/Vue-проект

В Windows PE этой сборки нет секций DWARF; PE debug directory пуст. Имена Go-файлов, функций, зависимости и reflection-метаданные сохранились, но исходные тела функций компилятор заменил машинным кодом. Их можно исследовать дизассемблером и по поведению создавать новую реализацию; это не восстановление оригинального текста и не гарантия эквивалентности.

Во встроенных файловых таблицах нет `.map`, `.vue` и исходных `.ts`. Минифицированные JS можно форматировать и читать, но оригинальные имена локальных переменных, Vue-шаблоны, комментарии и структура проекта автоматически из этого не возвращаются.

Наличие имени `internal/instances/routes.go` внутри EXE означает ссылку на исходный файл при компиляции, а не наличие его содержимого внутри программы.

## Как использовать результат

Игровые `.c` можно дорабатывать как код, после восстановления текстового конфига и настройки упаковки PBO. SQL можно использовать как исходную схему при отдельной реализации backend. `embedded/dist` можно изучать и использовать с совместимым API, но отдельно он не заменяет менеджер: запросы `/api/v1`, WebSocket, авторизация и игровые процессы требуют backend. Функциональная проверка панели и её серверной части на Windows здесь не выполнялась.

Каталог `web-assets` из предыдущего разбора сохранён для существующих ссылок. Его 71 JS/CSS-файл совпадает с файлами в `embedded/dist/assets`.

## Повторное извлечение

Из корня репозитория:

```bash
python3 tools/extract_release.py reference/v0.9.91/distr /tmp/addsm-restored
```

Скрипт проверяет SHA-256 обоих входных файлов, затем извлекает PBO, ресурсы embed.FS и метаданные. Он предназначен для этой конкретной версии, не является универсальным Go-декомпилятором. Никакие Windows-процессы при этом не запускаются.

Проверка встроенных ресурсов:

```bash
diff -r reference/v0.9.91/embedded /tmp/addsm-restored/embedded
```

Все эти материалы находятся в ветке `develop`. Исходный тег `v0.9.91` и готовые бинарники релиза не изменяются.
