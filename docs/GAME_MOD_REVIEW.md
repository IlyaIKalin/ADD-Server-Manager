# Проверка игрового мода ADD_Server_Manager 0.9.91

Проверен восстановленный Enforce-код из `reference/v0.9.91/game-mod`.
Это статическая проверка транспорта, команд, таймеров и счётчиков, не полный
аудит backend EXE и не проверка на запущенном DayZ Server.
В варианте `variants/engine-fps` исправлен только FPS. Остальные пункты ниже
сохранены в исходном виде и требуют отдельных изменений.
Ограничение каталога до первых 80 классов каждого раздела оставлено намеренно
по просьбе пользователя и не предлагается к исправлению.

## 1. Синхронный HTTP в игровом обновлении — высокий приоритет

`ADD_Http.c`, методы `Send`, `FetchConfig`, `GetNow`, `PostNow`:
используются `POST_now` и `GET_now`. `Send` вызывается из `Tick`, который
выполняется из `MissionServer.OnUpdate`. Опрос команд выполняется в системной
очереди вызовов игры. Поэтому ожидание HTTP-ответа задерживает игровой
скриптовый поток. Новый FPS-счётчик такие задержки учитывает, но не устраняет.

Следующий шаг: асинхронные REST callbacks с сохранением batch до подтверждения,
контролем одного запроса в работе, retry и корректным завершением миссии.

## 2. Невалидный HTTP-ответ может считаться успешным — высокий приоритет

`ADD_Json.c:ErrorCode` возвращает пустую строку при ошибке JSON-десериализации.
`ADD_Http.c:Handle` считает непустой ответ с пустым кодом ошибки успехом,
увеличивает `m_Sent` и не возвращает batch в очередь. Аналогично `PostNow`
может вернуть true для HTML/невалидного JSON. Например, HTML-страница ошибки
прокси вместо ожидаемого JSON может привести к потере batch без retry.

Следующий шаг: отличать валидный успешный ответ протокола от ошибки разбора,
проверять флаг `ok` и ожидаемую структуру ответа. Ошибки разбора повторять
с backoff, а не считать подтверждением.

## 3. Восстановление инвентаря может удалить вещи без полного восстановления — высокий приоритет

`ADD_CommandExecutor.c:RestoreGear` вызывает `ClearGear` сразу после разбора
JSON, до проверки возможности создать все предметы. `PlaceGear` при неизвестном
классе/нехватке места только пишет предупреждение и возвращается; `RestoreGear`
всё равно возвращает true. Пустой `raw` также превращается в пустой список.

Следствие: можно потерять текущую экипировку и получить частичную/пустую
замену с успешным подтверждением команды.
Следующий шаг: предварительная проверка, резервная копия, учёт ошибок каждого
размещения и стратегия отката. Не менять эту операцию без проверки на сервере.

## 4. Изменённые интервалы не перепланируют уже запущенные таймеры — средний приоритет

`ADD_Config.c:ApplyConfigJson` заменяет `Data`, но `ADD_Heartbeat.Start`,
`ADD_Positions.Start` и `ADD_Presence.Start` регистрируют повторяющиеся
`CallLater` с интервалом, прочитанным однократно. Повторное получение конфига
не удаляет и не пересоздаёт эти callbacks.

Следствие: изменение heartbeat/online/positions в панели во время работы
не меняет период уже зарегистрированных таймеров до перезапуска.
Следующий шаг: явное перепланирование при смене соответствующих полей.

## 5. Дисковая очередь не обеспечивает сохранность до подтверждения — средний приоритет

`ADD_Http.c:Tick` читает spool-файл и сразу удаляет его при переносе в RAM,
до успешной отправки. При неуспешном чтении также удаляет файл.
`SpoolAll` сохраняет RAM при штатном завершении, но не помогает при аварийном
завершении процесса между чтением и подтверждением HTTP.

Следствие: часть уже записанных на диск batches может потеряться при краше
или ошибке чтения. Это не гарантия очереди «никогда не теряем batches».
Следующий шаг: удалять устойчивую копию только после валидного подтверждения,
учитывая идемпотентность batch на стороне менеджера.

## Исправление FPS и проверка варианта

В исходнике счётчик увеличивался в `MissionServer.OnUpdate`, то есть после
ограничителя Expansion. В варианте счётчик в `3_Game/DayZGame.OnUpdate`
считает внешние callbacks, использует `GetTickTime` и исключён из клиента
через `#ifdef SERVER`. Сам транспорт и обход объектов остались в миссии.

Автотесты выполняют реальные тела методов счётчика через небольшой адаптер
C++: 12000 callbacks/с при скриптовых лимитах 100 и 500/с, разные скорости,
короткие heartbeat, сброс окон, повторное чтение и длительная пауза.
Отдельно проверяются исключение кода из клиентского препроцессинга,
контрольные суммы PBO, повторяемость сборки и неизменность всех исходных
файлов оригинального PBO, кроме `ADD_Ticker.c`.

Это не компиляция Enforce. Требуется проверка на сервере: отсутствие ошибок
скриптов, два heartbeat, сравнение с консолью на сопоставимом интервале,
работоспособность панели на обоих серверах. Точное совпадение с консолью
при разных окнах усреднения не гарантируется.
